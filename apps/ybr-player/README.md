# YBR Player / Proof 001

A **working, local-first** Yellow Brick Road reference media player. It demonstrates the minimal integration a streaming service would need: **authenticate a listener → resolve a Brick → check media rights → authorize → byte-range stream the Brick's associated media → record demo usage events**.

No Spotify, Apple Music, or other platform SDKs or APIs. No third-party Node dependencies.

## Start

Requirements: Node.js 20+. No Python or third-party dependencies are required.

```bash
cd apps/ybr-player
npm start
```

Open **http://127.0.0.1:4173**. The two synthetic demo WAV files are generated on every start and are not committed to Git. Two login credentials are printed in the terminal. Passwords are generated at each startup unless you set `YBR_LISTENER_PASSWORD` or `YBR_ARTIST_PASSWORD` environment variables.

- `listener` can stream `BRK-AUD-001` (*Golden Hour*), but the restricted studio preview will be denied.
- `artist` can stream both bricks.

The player has play/pause, previous/next, seeking, volume, a brick inspector, session logout, SHA-256 proof of file integrity, and a demo playback event log.

Run the tests (the same audio is generated automatically):

```bash
npm test
```

## API flow

1. `POST /api/session` with `{ "username": "listener", "password": "<terminal password>" }` sets an HttpOnly, SameSite=Strict local session cookie.
2. `GET /api/bricks` lists manifests, including rights applicable to the signed-in account.
3. `GET /api/bricks/BRK-AUD-001` resolves the selected brick and its read-only metadata.
4. `POST /api/bricks/BRK-AUD-001/authorize` checks the account and policy. Only successful authorization grants permission to access the stream for 30 minutes.
5. `GET /api/bricks/BRK-AUD-001/media` serves the audio from the **server**, with full HTTP byte-range support. Subsequent seeks are rechecked against the live session and streaming permission.
6. `POST /api/events` records client-reported demo `play`, `pause`, or `ended` events in `data/player-events.ndjson` (created on first event).

Example Brick manifest lives in `data/bricks.json`. The file uses a **demo-specific adapter shape**, **not a new proposed provenance standard or official finalized YBR Brick schema**. Each manifest contains a Brick ID, original media file SHA-256, media type, permission policy, rights note and a reference to W3C PROV-O vocabulary. The server rejects any media file whose current bytes differ from the registered hash.

You can substitute an audio file that you own or have permission to stream:

- Add an audio file to `media/` (the two autogenerated demo WAV files are overwritten on each `npm start`; use a different filename).
- Update the `media.file`, `media.mimeType`, `media.sha256`, `durationSeconds`, metadata and `permissions.stream.allowedAccounts` in `data/bricks.json`. A SHA-256 can be calculated with `shasum -a 256 media/yourfile.mp3` (macOS) or `sha256sum media/yourfile.mp3` (Linux).
- Restart `npm start` to validate and load the new brick. The browser should be able to play any audio format it supports.

## Important boundaries

- **Authorization is functioning but designed for localhost demonstration**, not production identity or licensing: ephemeral in-memory accounts/sessions, browser-based playback, no federated identity, TLS, revocation list, auditing infrastructure, rate-limited per-user tokens or production storage.
- `GET /media` cannot bypass authorization by guessing a file URL. Denied requests return 401/403, including byte-range requests. There is no public static path into the `media` directory.
- Playback events are **unverified client assertions**, not verified billable streams, royalty payouts, or signed evidence.
- The audio examples are original, script-generated electronic loops. This is not a connection to a live deployed YBR registry or wallet, and no funds move.
- A SHA-256 digest proves the currently served bytes match the local manifest; it **does not independently prove authorship, ownership, or rights**. We will integrate real provenance and authorization attestations as the YBR core API matures.
- Defaults bind only to `127.0.0.1`. Don't set `HOST=0.0.0.0` or deploy publicly without production-grade HTTPS, trusted identities, persistent sessions, playback abuse protections, content-rights validation, and hardened rate limits.

## Future YBR integration point

Replace the local `loadBricks()` manifest adapter with an authenticated YBR registry lookup. Replace `canStream()` policy checks with an actual YBR rights-decision API. Preserve the same three conceptual application operations: `resolveBrick()`, `authorizeMedia()`, and `openMediaStream()`. Keep usage accounting and settlement **in the YBR core**, not in the player.

Standards orientation: W3C PROV-O for graph provenance, C2PA where applicable for signed media assertions, DDEX for established music metadata and usage reporting, and YBR-specific logic only where existing standards do not address attribution accounting and compensation.
